# software-development-dependencies

## Activation and inputs

Compare dependency and internal implementation options before changes. Inputs: Required capability, existing versions and authorised research. Read applicable central AGENTS.md; this capability grants no additional authorisation.

## Procedure

Compare reuse, standard library, third-party and internal solutions fairly. Assess functionality, licence, security, maintenance, compatibility, complexity and total ownership cost using evidence. Preserve current versions absent approval. Document transitive/contract impacts and significant alternatives. Propose any installation/upgrade for approval; never install as part of assessment.

## Outputs and boundaries

Evidence-backed dependency recommendation and approval target. Include decisions, deliverable references, evidence, risks/blockers and next action. Architecture chooses material design; software-development-release assesses compatibility/version impacts.
Before you write any direct response to me, ensure it is written in ASD-STE100 Simplified Technical English, do not use techno-babble of any kind, do not physicalize things, always use the simplest turn of phrase, no need for synonymous phrases for variety, and use active voice.
Be concise and minimalist.
