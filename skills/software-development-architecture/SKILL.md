# software-development-architecture

## Activation and inputs

Evaluate boundaries, dependency direction and architectural alternatives. Inputs: Approved requirements and existing architecture/code. Read applicable central AGENTS.md; this capability grants no additional authorisation.

## Procedure

Before analysis, identify the material choices and ask the user focused questions. Offer options and recommendations. Brainstorm alternatives and failure scenarios with the user before recommending a design. Do not substitute assumed requirements for missing answers.

Trace components, data flow and reuse. Compare at least two credible alternatives for material choices across complexity, security, scalability and ownership. Check dependency direction and cycles. Evaluate patterns and SOLID pragmatically. Document significant decisions and aligned Mermaid component diagrams. Present the result and wait for approval before the next stage.

## Outputs and boundaries

Architecture proposal, alternatives and constraints. Include decisions, deliverable references, evidence, risks/blockers and next action. 
software-development-dependencies supplies library trade-offs; software-development-design details contracts.
